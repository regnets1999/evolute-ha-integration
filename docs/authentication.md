# Авторизация Evolute

## Получение и хранение токенов

Пользователь переносит в Home Assistant две cookies из своей браузерной сессии EVassist. `validate_input()` проверяет пару запросом списка автомобилей. После успешной проверки в `ConfigEntry.data` сохраняются актуальные `access_token` и `refresh_token`, включая возможную ротацию во время проверки. При повторной авторизации обновляются только эти два поля существующей записи.

При запуске `async_setup_entry()` создаёт клиент из сохранённой пары. Во время работы callback `_persist_tokens()` передаёт обновлённые значения в `hass.config_entries.async_update_entry()` с сохранением остальных полей записи. При неуспешной проверке в форме запись не создаётся и не обновляется.

## Идентификация аккаунта и повторная авторизация

- `get_account_id()` читает непустой строковый `_id` или `userId` из access JWT. Декодирование JWT извлекает идентификатор. Доступ кандидата подтверждает запрос к API, после которого берётся ID из актуального токена. При первичной настройке этот ID становится `unique_id`. Если подходящего поля нет, запись не создаётся.
- `_validate_reauth()` определяет владельца записи по сохранённому access JWT. Истёкший JWT подходит для сравнения идентификаторов, поскольку новый доступ проверяется отдельно. После проверки новой пары идентификатор сверяется с прежним. При несовпадении, отсутствии ID или изменении подтверждённой идентичности записи во время проверки reauth отклоняется без записи токенов и перезагрузки.
- Старый `unique_id` может содержать фрагмент прежнего refresh-токена или отсутствовать. Проверка работает по сохранённому access JWT независимо от происхождения `unique_id`. Если из сохранённого токена нельзя установить владельца, reauth не заменяет токены. `unique_id` и `entry_id` существующей записи сохраняются.
- При обычном refresh рабочий клиент с известным ID сверяет аккаунт до применения и сохранения выданной пары. Это защищает от переключения аккаунта, если access-токен прошёл первоначальную проверку, а принадлежность refresh-токена стала видна только при ротации. Для старой записи, запущенной без ID в сохранённом access JWT, сохраняется прежнее поведение фонового refresh.

## Повторная авторизация, добавление и удаление записи

- **Reauth** обновляет токены в существующей записи и перезагружает её по тому же `entry_id`. Идентификаторы сущностей формируются из локального UUID автомобиля и ключа сущности. Хранилище UUID отделено от токенов, поэтому reauth сохраняет эти идентификаторы. [Условия сохранения UUID](compatibility.md)
- **Повторное добавление** проверяет подтверждённый ID нового аккаунта штатной проверкой `unique_id` и локально сравнивает его с ID из сохранённых access JWT записей Evolute. Совпадение приводит к `already_configured`, в том числе если у прежней записи legacy `unique_id` или он отсутствует. По существующим записям сетевых запросов нет. Если из сохранённого JWT нельзя извлечь ID, локальное сравнение не подтверждает совпадение, а штатная проверка `unique_id` продолжает действовать.
- **Добавление после удаления** создаёт новую запись, если действующая запись этого аккаунта больше не найдена. Защита от дубликатов проверяет только существующие записи и не восстанавливает удалённую конфигурацию. Удаление может привести к потере привязок. Сохранность истории и её сопоставление с сущностями новой записи не гарантируются.

При переходе с оригинальной версии 1.4.3 после установки пакета форка создайте новую запись Evolute. Reauth применяется к уже настроенной записи и не заменяет [процедуру чистой установки](marketplace.md#переход-с-исходного-репозитория).

## Обновление и параллельные запросы

Клиент отправляет оба токена как cookies. `401` на защищённом запросе запускает одну попытку обновления через `/id-service/auth/refresh-token` с refresh-токеном в теле. Для запроса списка автомобилей первое `403` также запускает обновление. После успеха клиент повторяет исходный запрос с актуальной парой. Если ответ обновления не содержит нового refresh-токена, клиент сохраняет прежний.

`_async_refresh_if_needed()` защищает обновление через `asyncio.Lock` в пределах одного экземпляра клиента. Запрос запоминает отправленную пару и объект попытки. Под блокировкой клиент сверяет их с текущим состоянием. Если пара обновилась, запрос использует её без второго refresh. При сбое запросы, которые уже были отправлены для той же попытки, получают ту же категорию ошибки. Новый запрос может повторить попытку после сбоя.

## Классификация ошибок

| Ответ или сбой | Реакция клиента |
| --- | --- |
| Первый `401` от защищённого запроса, первый `403` от списка автомобилей | Попытка refresh и повтор запроса при успехе. |
| `401` или `403` от endpoint обновления | `EvoluteAuthError`. Сервер отклонил восстановление сессии. |
| Повторный `401` от списка автомобилей с актуальной парой после refresh | `EvoluteAuthError`. Сервер отклонил и обновлённые данные аккаунта. |
| Рабочий refresh вернул access JWT другого аккаунта | `EvoluteAuthError`. Ранее принятая пара остаётся без изменений. Если в новом JWT отсутствует ID, возвращается `EvoluteProtocolError`. |
| `403` на запросе отдельного ресурса, повторный `403` от списка автомобилей или повторный `401` на запросе отдельного ресурса | `EvoluteRequestError`. Отказ относится к операции и сам по себе не инициирует reauth. |
| `5xx`, `408`, `429`, ошибка соединения или тайм-аут, в том числе при refresh | `EvoluteUnavailableError`. Клиент сообщает о временном сбое. |
| Повреждённый JSON, неожиданная структура или ответ refresh без корректного access-токена | `EvoluteProtocolError`. Некорректный ответ не инициирует reauth. Пустое тело разрешено там, где его допускают endpoints команд. |

## Реакция Home Assistant

- **Форма настройки и reauth.** Показывает отдельные ошибки для неподтверждённого доступа к операции, неверных токенов, недоступности сервиса и некорректного ответа. Пользователь может повторить проверку, данные формы при сбое не сохраняются.
- **Загрузка записи.** Подтверждённый отказ переводится в `ConfigEntryAuthFailed`, и Home Assistant запускает штатный reauth. При временном сбое, некорректном ответе или отказе отдельной операции на обязательном запросе загрузка откладывается через `ConfigEntryNotReady`.
- **Фоновый опрос.** Подтверждённый отказ также передаётся через `ConfigEntryAuthFailed`. При сбое отдельного автомобиля сохраняются результаты успешных запросов по остальным. Если телеметрию получить не удалось ни для одного автомобиля, координатор возвращает ошибку через `UpdateFailed` и продолжает плановые попытки. При временном сбое запроса сервисных данных сохраняется их предыдущий кэш до следующей попытки.
